# CRISP-DM Adaptation for Simulation-Based Multi-Agent RL

**Phase:** Initiation (W1–W3) · **Status:** Draft for review · **Owner:** R3 (MLOps & Deployment Lead)

---

## 1. Why CRISP-DM needs adapting here

CRISP-DM assumes a **fixed dataset** that exists before modelling and is unaffected by it. Every
phase boundary depends on that assumption: Data Understanding precedes Modeling because the data is
already there to be understood; Evaluation is trustworthy because the test split was carved from a
static corpus.

Reinforcement learning breaks the assumption at its root:

> **The data is generated by the policy being trained. Changing the model changes the dataset.**

Three concrete consequences:

1. **Data Understanding cannot be done once, up front.** The state distribution a trained QMIX fleet
   visits is nothing like the distribution a random policy visits. "Understanding the data" before
   training tells you about the *environment*, not about the data the model will actually learn from.
2. **Data Preparation is not cleaning — it is environment design.** There is nothing to impute or
   de-duplicate. The analogous activity is specifying the floor plan, reward function, observation
   space, and episode termination rules. These are *modelling decisions disguised as data decisions*,
   and they have far more influence on the outcome than any hyperparameter.
3. **Train/test leakage takes a different form.** There is no row-level overlap to worry about.
   Leakage here means *tuning against the evaluation set* — iterating on reward shaping or the floor
   plan while watching evaluation scores. This is subtler and easier to do accidentally.

We therefore retain CRISP-DM's six-phase structure (it is the course framework and it genuinely
helps) but restate each phase's content, and add two RL-specific control mechanisms.

## 3. Two additions CRISP-DM does not provide

### 3.1 Pre-registration (guards Evaluation)

Because the "dataset" is generated on demand, nothing physically stops the team from regenerating an
evaluation manifest that happens to flatter QMIX. The countermeasure is procedural and borrowed from
experimental science:

1. Manifests for N=5/10/20 are generated in W4, **before** any training run.
2. SHA-256 hashes recorded in `data/manifests/HASHES.txt`; commit tagged `eval-manifests-sealed`.
3. Every evaluation run verifies the hash and aborts on mismatch.
4. Hypothesis **H1** (NFR-2: the QMIX−IQL gap is non-decreasing in N) is written down in W3, before
   any result exists, along with the commitment (ETH-5) to report it whichever way it falls.

Git history is the audit trail: the manifest tag must predate the first training commit. This is
checkable by an examiner in one command, which is the point.

### 3.2 The iteration boundary (guards Modeling ↔ Environment Specification)

CRISP-DM's backward arrows encourage revisiting Data Preparation after Modeling. In RL that arrow is
dangerous: changing the floor plan or reward function after seeing evaluation results is *tuning on
the test set*, and it silently invalidates every earlier run.

**Rule.** After the W4 environment freeze, the arrow from Modeling back to Environment Specification
requires:

- a written ADR stating what changed and why,
- re-running **all** algorithms on the new environment (no mixing results across env versions),
- MLflow's `env_config_hash` tag making cross-version comparison impossible to do by accident.

Reward-weight changes are the one exception, and only because they are the explicit subject of the
Optuna study (OBJ-5) — but that study tunes on *training* seeds and reports on the sealed manifest
once, at the end.

## 4. Where the loop is genuinely different

```
   Business Understanding
            |
            v
   Environment Understanding  <---+
            |                     |
            v                     |  W4 only: fast iteration
   Environment Specification -----+  (calibrate difficulty, fix deadlocks)
            |
            |  === FREEZE (M2 gate) ===
            v
        Modeling  <-------+
            |             |  free iteration on TRAINING seeds
            v             |  (hyperparameters, reward weights)
      Training eval  -----+
            |
            |  === SEAL BROKEN ONLY ONCE ===
            v
   Evaluation on sealed manifests   (one shot per algorithm × N)
            |
            v
        Deployment
```

The critical structural difference from classical CRISP-DM: there are **two evaluation loops**, and
only the inner one may be iterated. Training-seed evaluation is a development instrument used
freely; sealed-manifest evaluation is a measurement, taken once per configuration. Conflating them
is the standard way RL papers become irreproducible, and keeping them apart is a specific
contribution this project can point to in the report.
